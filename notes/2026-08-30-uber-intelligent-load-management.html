1. 文章总结

背景。Uber 的自研分布式数据库 Docstore 和 Schemaless(建于 MySQL 之上)支撑全公司所有业务线:几千个集群、几十 PB 数据、每秒几千万请求。在这个规模上,局部过载会级联放大(超时 → 重试 → 更过载),且多租户共享底层资源,必须同时解决过载保护和租户公平两个问题。

失败的第一版:routing 层的静态配额。给每个租户按"处理字节数"定容量配额,用中心 Redis 记账,超了返 429。四个死因:每个请求多一跳 Redis(新故障点);无状态路由层看不见几千个存储分片的真实健康;成本模型失真(全表扫描和单行读计费相同——请求的真实成本在执行前不可知);静态配额需要无止境的人肉调整。关键教训:过载控制必须住在离数据最近的地方(存储层),并且要用自我校准的信号。

演进三代:

代机制解决了遗留问题
一代CoDel 队列(按等待时间拒 + 过载时 FIFO→LIFO)+ Scorecard(租户并发上限)+ regulators(写字节/热点/内存/线程保险丝)机器压不垮了;肇事租户被隔离拒人不分贵贱;参数写死;固定超时引发重试潮(thundering herd)
二代Cinnamon:优先级 t0–t5 从低往高砍;PID 控制器驱动砍人比例;超时阈值由 P90 动态定;auto-tuner 动态找并发上限 N用户流量被优先保护;零人肉调参;shedding 从锯齿变平滑只感知本地健康;远程信号(follower 落后)靠外挂 token bucket,多脑决策打架
三代统一引擎 + BYOS(bring your own signal):所有信号(本地+远程)插件化,喂进唯一决策环;按信号性质选择"按优先级砍"或"按肇事者砍"决策一致、可观测归一、加新信号零边际成本—

实测收益(对比 token bucket 时代,过载期间):吞吐 +80%(5,400 vs 3,000 QPS);P99 延迟 −70%(1.0s vs 3.1s);goroutine −93%(峰值 1 万 vs 15 万);内存 −60%(1GB vs 5–6GB 尖峰)。

文章的 lessons:优先级是第一位的;fail fast 别憋着;PID 让 shedding 平滑;控制放在 source of truth 旁边;拥抱动态、拒绝静态配置;投资可观测性;简单优先。

2. 一个请求的完整旅程(end to end)

2026-09-11 补写。原总结按时间线讲了"有哪些零件",没讲一个请求进来之后按什么顺序碰到它们。以下按 Cinnamon 时代(二代/三代)的路径写,细节部分参照了 Uber 2023 年专讲 Cinnamon 的系列博客。

0. 前提:所有控制都在 storage node 上,按 partition 的 leader 逐个执行。Router 层无状态,只做解析和路由。每个节点用的是基于并发数的限流(同时在处理几个请求),不是 TPS:请求的成本事前不可知,并发槽按"占用时长"自动结算,大请求自然多付费。

1. 到达,带 priority tag。请求带着 t0–t5 的 tier 到达(t0 infra、t1 用户正在等的请求、t5 离线/报表/重试),标签由 caller 服务或请求元数据决定,storage node 不猜。

2. Scorecard:按 tenant 查 in-flight quota。这个 tenant 在本节点上已接收、尚未返回的请求数(排队中 + 执行中)是否超过它自己的上限,超了当场拒,只拒它,不看系统忙不忙、不看 tier、不看 P90。这是"按肇事者砍"那条路径。quota 是静态配置的规则表(图 6 "Scorecard rules"),三个 rejection point 里唯一静态的一个,原因见原则 16。(原文只说 "concurrency limits",未明确是否含排队中的请求;按其隔离目的推断为含。)

3. Rejector:enqueue 之前,按 tier 砍掉一个比例。这是主力 rejection point。后台 PID controller 盯着队列的 inflow 和 outflow,进多出少说明在积压,就调高"本轮该砍的比例";队列清空后再慢慢降。PID 只维护这一个量(砍的比例),队列的 wait time threshold 和 in-flight limit N 分别由另外两个机制管,见第 5、6 步。比例也不是随机概率:30% 意味着算出一条 cutoff,让低于它的那确定的 30% 流量被拒。Rejector 拿到比例后,用最近各 tier 的流量占比算出一条 cutoff(落在某个 tier 的某个 cohort),优先级低于 cutoff 的当场拒,高于的 enqueue。因为 cutoff 从 t5 往上滑,砍的永远是最不重要的那部分;tier 内再按 caller hash 分 cohort,同一个用户要么全过要么全拒,不会一半一半。

4. enqueue:两个 in-memory priority queue。只按读、写分两个队列(重要性已由 tier 表达,不再按业务分队列)。队列内 dequeue 顺序按优先级,t1 永远先于 t4 被处理。

5. 队列超时:enqueue 之后的兜底。每个请求记着到达时间。等待超过 threshold 的被清掉,threshold 不是配置,是跟随最近 window 内实测的 P90 latency:

threshold(现在) = k × P90( 最近 window W 内已完成请求的 latency)
拒绝条件:  现在 − 到达时间 > threshold

原理:arrival rate ≤ throughput 时,一个请求最多等"一个处理时间";
     等得比这更久 = 队列在积压 = 需求已超容量,多处理一个也不会更好。
     取 P90 而不是均值,是给正常的慢请求留余量,不误判。
     用旧 window 不是"预测",是"最近一次测量",threshold 滞后真实情况一个 window。

这个 threshold 没有反馈环,不经过 PID:它只是在描述"处理一个请求大概要多久",直接测就行;PID 用在"有目标要逼近"的地方(让 inflow 等于 outflow)。正常情况下 rejector 已经砍够,这一层几乎不触发;它防的是"放进来之后 throughput 突然掉了"。
FIFO/LIFO 与 tier 的关系:tier 之间始终按优先级 dequeue,t1 永远先于 t4;FIFO/LIFO 只决定同一 tier 内取最老的还是最新的。检测到积压时切 LIFO,让还来得及的新请求先走,老的由超时清掉。一代 CoDel 的切换判据是"最近 window 内等得最少的请求也超过 target"(连最幸运的都在等,积压是结构性的);Cinnamon 时代是否沿用此判据,原文未明说,且 rejector 已在门口控量,队列内积压少,LIFO 作用比一代小。

6. Scheduler:出口按 in-flight limit N 放行。N 由 auto-tuner 动态找:看整体吞吐和延迟,加法慢慢涨、延迟恶化时乘法砍,停在吞吐最高的那个 N。放行的请求执行,in-flight 计数 +1,结束 −1。

7. 旁路信号:regulators 与 BYOS。四个节点本地 regulators(写字节、热点 key、内存、goroutine 数)平时几乎不触发,触发时作为 overload signal 喂进同一个 control loop;远程信号(follower commit lag)通过 BYOS 插件同样喂进来。统一引擎按信号性质分流:系统性压力 → 走 rejector 按 tier 砍;某个 tenant 作恶 → 走 Scorecard 只砍它。

三个可调的量,三个不同的机制(纠正本文原句"PID adjusts queue timeouts and inflight limits"给人的印象,按 2023 年 Cinnamon 系列原文):

可调的量谁在调输入怎么调
砍掉的比例 → tier cutoffPID controller队列 inflow vs outflow进多出少就升,清空后慢慢降
队列 wait time threshold统计跟随,非 PID最近 window 的 P90 latencythreshold = k × P90(2023 年系列里还是固定的"request timeout 的 33%",本文才改为跟随 P90)
in-flight limit Nauto-tuner整体吞吐 + latency加法慢涨,恶化时乘法砍
rejection point时机依据角色

标注:Scorecard 位于 rejector 之前、regulators 与队列并行,这两处顺序是按组件职责推出的,两篇原文均未明说。tier 内 cohort 的具体数量未核实。

3. 核心争论:为什么用 concurrency 不用 TPS

这是我花最多轮讨论、也是收获最大的部分。完整推导链:

机器的真实约束是工作量/秒(我的原始观点,正确)→ 但工作量在门口不可测(Uber 第一版给请求标价失败的原因)→ 工作量必然表现为占用时长(机器速度固定,活多的必然待得久)→ 占用时长可以在门口"数在场人数"来限制 → 所以限并发就是限工作量,计费方式从"事前预测"(做不到)变成"事后按时长自动结算"(免费)。

数字验证:10 个座位,小请求占 1ms、大请求占 100ms。全是小请求时放行 10,000 个/秒,全是大请求时放行 100 个/秒——个数差 100 倍,放进机器的工作量完全相同。任何固定 TPS 做不到这种自适应。

重要的边界(我提出的质疑,全部成立并对应架构组件):

  • 占座 ≠ 干活(等下游、等锁)→ 需要 regulators 补盲区
  • constant N 在流量构成变化时非最优 → 需要 auto-tuner 动态找 N
  • adaptive 本质是 reactive → 目标不是预测准,是误差有界 + 秒级自愈

TPS 限流的正确位置:数字是政策(配额/合同/防滥用)时就该 constant;数字是容量估计时才需要 adaptive。多数公司用"constant limit + 大余量 + autoscaling(动容量)"就够了;Uber 的存储是有状态的,容量短期焊死(扩 MySQL 分片要挪数据、以小时计),只能让准入变聪明——stateless 动容量,stateful 动准入。

4. 七站机制拆解

第 1 站:等候区 —— 为什么光有计数器不够

流量是一阵一阵的,"满"往往只持续几毫秒。座位满直接拒 = 为一个 5ms 后自动消失的拥堵付出完整失败代价。队列的本质:用几毫秒延迟换掉大量误杀,把"瞬间的满"和"真过载"区分开。它是减震器,不是等候室——毒性(内存、backlog)由第 2 站的时间上限锁死。

第 2 站:按等待时间拒,不按队伍长度

拒人的尺子必须和被保护的东西同单位:调用方(同步阻塞,预算几百 ms)买单的是时间。队伍长度不含信息(同样 100 人,机器快时无害、机器病时致命);等待时间直接反映调用方耐心消耗,且自动锁死内存(队里最多站着"最近几 ms 到达的人")。

判断拥堵的精巧细节:看最近窗口内最幸运请求的等待是否超标(连运气最好的都超了,拥堵才是结构性的)——用最小值抗噪,不用均值。

设计手法:能直接测量目标量,就绝不估算中间量(不需要估算"处理速度",它的影响已全部灌进等待时间里)。

第 3 站:过载时 FIFO → LIFO

过载时队头 = 等得最久 = 调用方预算几乎烧完 = 最接近死亡的请求。FIFO 的行为:把最宝贵的产能投资给最快过期的资产(做完答案没人要 = 无用功),同时让队尾新鲜请求排队变老。修复:检测到拥堵(复用第 2 站的信号)就翻转成后进先出;老请求由等待超时清走。LIFO 保证产能喂活人,超时保证死人被清走。过载时"对个体公平"让位给"存活工作价值最大化"。

第 4 站:优先级 t0–t5

过载多由后台流量(管道/聚合/清理)引发,却砍到用户流量。修复:请求带优先级标签,t0(关键基础设施,保留档)/ t1(用户正在等的在线请求,真正的保护对象)/ … / t5(最不急的后台活)。过载时从 t5 逐层向上砍。平时全部机制休眠,人人平等(急诊分诊,不是贵宾通道)。

标签怎么来:档位语义中央定义、t0/t1 收紧;在 API 边缘按业务流集中配置(不是各服务自己贴);像 trace id 一样塞进请求上下文沿调用链透传(同一个共享存储,叫车链路的查询带 t1、报表任务的查询带 t5);没标签的按调用方给默认档。

防通胀:标签必须有价格。Amazon 的 ORR + bar raising 就是价格的现实实现——t1 是一摞签了字的义务,不是荣誉。治理层(月级,人)+ 执行层(纳秒级,透传)缺一不可。

第 5 站:三个自动环(本文的数学心脏)

2026-09-11 更正:下面环 1 写的"误差 = 实测等待 − 目标等待"是 8 月 30 日的推断,与 Cinnamon 系列原文不符。原文:"it monitors the inflow and outflow of requests into the priority queue... Based on these numbers, it uses a PID controller to determine a ratio of requests to shed." 即 PID 的输入是 inflow vs outflow,目标是两者相等;PID 只输出砍的比例这一个量。队列 timeout 在 2023 年系列里是"正常 request timeout 的 33%",到 2026 年本文才改为跟随 P90 latency,且它不经过 PID。环 2、环 3 的内容不受影响。详见第 2 节和 Q23/Q26。

环 1:PID 推水位线(追踪已知目标)。先把 boolean 升级成有大小方向的误差:

误差 e = (实测等待 - 目标等待) / 目标等待

调整量 u = Kp × 当前误差          ← P:看现在(超得越多砍得越狠)
         + Ki × 历史误差累计       ← I:看过去(一直差一点,攒够就出手)
         + Kd × 误差变化速度       ← D:看趋势(在好转就提前松手,防过冲)

新砍人比例 p = 旧 p + u   (卡在 0%~100%)

三级传动把比例变成可执行的线:PID 推 p(如 26%)→ 查最近 1 秒流量成分直方图,从最低档累加到 26% → 水位线 = (档位, cohort 格号),如 (t4, 格32)。档内按调用方身份哈希分 128 格,保证同一调用方"要么正常要么干脆暂停",而非人人随机抽风。慢环(500ms)画线,快路径(每请求,纳秒)只比大小。拒绝发生在进门那一刻;直方图是"用刚过去 1 秒预测未来 500ms"——赌注极小、错了下一拍自动纠。

PID 出身:1922 年 Minorsky 为军舰自动舵发明,把老舵手的手感(按偏航打舵/顶住洋流/提前回舵)翻译成数学。Uber 的贡献不是发明而是识别同构。注意 I 项要配遗忘机制(integral windup:记仇的项必须会过期)。

环 2:目标等待 T_target 由 P90 自定。"等多久算不正常"只相对于"这里的活平时要干多久"才有意义(1ms 单行读集群 vs 500ms 扫描集群不能用同一个数)。每台机器取自己最近请求耗时的 90 分位当基准。防反馈污染:喂标准的数据(干活时长)必须和要检测的病症(排队时长)不同源,再加绝对上限封顶。

环 3:auto-tuner 找座位数 N(寻优未知峰顶)。N 和吞吐是山形关系(太小吃不饱、过头互相踩踏),且峰会漂移——目标未知,PID 无从下手(PID 需要已知 setpoint + 单调旋钮),只能试探爬山。祖师爷是 TCP 的 AIMD:

没堵: 窗口 = 窗口 + 1      ← 朝危险方向蹑手蹑脚
堵了: 窗口 = 窗口 × 0.5    ← 朝安全方向夺路而逃
(错误代价不对称 → 步长不对称;到了峰顶仍 +1 = 持续付费买"峰在哪"的情报)

服务版用"延迟膨胀率"当坡度计(Netflix gradient 公式,Uber auto-tuner 同族):

新 N = 旧 N × (空载延迟 / 当前延迟) + 探测余量
// 当前延迟 ≈ 空载延迟 → 比值≈1,轻轻上探
// 延迟膨胀 2.5 倍 → 比值 0.4,大幅收缩(膨胀 = 内部在排队,Little's Law)

三环速度刻意错开(纳秒规则层 / 500ms PID / 秒级 tuner):两个反馈环速度接近会互相追逐共振——环速错开是控制工程铁律。

第 6 站:两个配角 —— Scorecard 与 regulators

Scorecard(租户公平闸门):写死的规则表,常年在岗:"每租户在本机各类操作最多同时占几个座"。全系统唯一故意不自适应的组件——它执行的是政策不是容量估计,契约的美德是恒定可解释。事故时肇事者自动现形、自动被关进自家院子。

Regulators(专项保险丝):补"占座≠干活"的盲区:写入字节(低频大写打满 I/O)、热点分区键、剩余内存、goroutine 数。各盯一个死角,平时永远沉默,越线熔断。

第 7 站:统一大脑 + BYOS

历史问题:远程信号由外挂 token bucket 处理,多个组件独立决策 → 脑裂(split-brain):互相不知情地重复砍、或把对方砍人的波动当新信号,追逐震荡。修复:只留一个决策点,所有信号(本地:排队/内存/写入量;远程:follower commit lag)插件化喂进同一个环。信号声明性质 → 系统性压力按优先级砍,某家作妖按肇事者精准掐。红利:可观测归一 + 加新信号零边际成本(rate limiter → load management 平台)。

commit lag 全链路:quorum(3 副本 2 票提交)故意不等最慢 follower——好处是快,代价是最慢者可以无限落后而 leader 毫无感觉(冗余无声蒸发:表面 3 副本,实际容错不足 1 台)。信号免费:Raft leader 本来就维护 matchIndex[](不记就没法数票定提交线),落后量 = leader 最新编号 − matchIndex[B],一个减法,搭共识协议已有通信的便车,不新建任何全局组件。

5. 我的疑问与解惑

按时间顺序记录我卡住的地方和解开的方式——这部分是这份笔记区别于原文的价值所在。

Q1:用 max concurrency 而不是 max TPS 定容量,是行业标准吗?

过载保护领域是强共识(TCP 四十年先例、Netflix/Envoy/连接池),但不是唯一工具:TPS 限流统治政策/配额/边缘场景。concurrency 是闭环测量,TPS 是开环预测。

Q2:我在 Amazon 做的"压 TPS 到延迟拐点"的 load test 错了吗?

没错,那是标准容量规划。错的是把快照当运行时阈值。拐点(knee)= 延迟曲线从平地陡然上翘的弯点;而 knee 处的 TPS × 延迟 = 并发容量,后者才是跨场景稳定的不变量。

Q3:concurrency limit 有个大假设——资源真的受并发数约束吗?资源明明受工作量约束。

前提对,结论反转:正因为工作量事前不可测,才必须用"按占用时长自动结算"的并发槽。concurrency 不是资源,是可执行的代理:latency 是传感器,concurrency 是执行器。

Q4:悖论——一个 slot 既能 serve 10ms 也能 serve 100ms 请求,不需要区别对待吗?

区别对待确实发生了,但在时间维度自动完成:大请求占座 10 倍久 = 被收 10 倍费。slot 恒定供应"占座时间",工作量恒定,个数自动浮动。

Q5:停车场车位是 constant 的,长停日 serve 的车少,资源不是没用满吗?

混淆了"车次"和"车位·小时":长停日停车场同样 100% 满,资源全部卖出,只是给了更贪的客户。但"占座≠干活"时(等下游)质疑成立 → 所以 N 需要 auto-tuner 动态找。

Q6:现实里 constant TPS 遍地都是,adaptive 很少见,怎么解释?

大多数 rate limit 干的是政策工作(配额/合同/防滥用),constant 是需求本身;干容量保护的多靠"余量 + autoscaling(动容量)"。adaptive 准入只在容量焊死(stateful)+ 规模大的地方成为必需。

Q7:adaptive threshold 本质是 reactive,用现在预测未来,不准啊?

它不是预测器是恒温器:评价标准不是预测准,是误差有界 + 秒级自愈。static 的误差以周为单位靠人修,adaptive 以秒为单位自动修。且 concurrency 是"过期了也安全"的旋钮(座位计时效应兜底)。

Q8:不用 Redis,全局计数怎么做?

全局计数被取消了:concurrency 被定义成每台机器的本地物理事实(内存里一个原子整数,+1/−1,精确免费)。全局效果 = 局部守门自然叠加(TCP 同款);真正的远程信号(commit lag)搭 Raft 已有通信便车。难题不是被解决的,是被重新定义掉的。

Q9:用 token bucket 解决 burst 行不行?

不行:令牌按墙上的钟恒速入账(与机器死活无关,骨子里还是 constant TPS),且桶存款会把整个 burst 一次性砸进机器,然后急刹车——"猛灌-饿死"锯齿。队列按"有人干完离开"放行,被机器真实消化速度驱动。token bucket 解决的是政策世界的 burst(别误伤守约但突发的客户)。

Q10:我不敢随便 queue request——MySQL 调用是同步的,而且 backlog 有连锁反应(retry storm、清 backlog 压垮下游)。

两条顾虑正是设计的两条边界:队列预算是几毫秒不是几秒(减震器);时间上限自动锁死内存。我的 OpenSearch 事故 = metastable failure 教科书(病因移除后故障靠 backlog+retry 自持;清 backlog = 重放昨天的高峰);最后的"老消息进 DLQ"= 手写了一个 CoDel。

Q11:队头不是"等待时间最短"吗,马上就轮到它了?

队头距被服务最近,但已烧掉的预算最多(预算烧的是已等时间)。过载时服务队头 = 给剩 100ms 预算的请求做 150ms 的活,做到一半对方挂断。超市先卖临期酸奶是对的,但快递要 3 天时就不对了。

Q12:P90 超标只是个 boolean,怎么推得动连续的水位线?

第 0 步先把 boolean 换成有大小方向的误差((实测-目标)/目标),之后 PID 三项 → 调整量 → 砍人比例 → 直方图换算 → (档,格) 水位线,全程连续。boolean 只能驱动开关(锤子),误差才能驱动比例(调光旋钮)。

Q13:调整量怎么 translate 到 reject 标准?砍是在门口还是门内?

三级传动:调整量推状态变量 p → 查流量成分直方图把 26% 换算成 (t4, 格32) → 挂在门口。拒绝全部发生在进门瞬间(纳秒级比大小),进了队的人不被水位线赶出去;直方图用过去 1 秒预测未来 500ms,错了下一拍纠。

Q14:所以不是进门的时候 reject,而是进门之后 reject?

拒绝就发生在进门瞬间,进了队的人不会被水位线赶出去。慢循环(每 500ms)回头看刚过去 1 秒的流量构成、画好线挂在门口;快路径对每个新到达的请求做一次比大小。"砍 26%"是个预测:用已经发生的事情赌未来 500ms——赌注极小、错了下一拍自动纠、代价有界。反馈控制的本质:把"做对一个大预测"换成"快速迭代一万个 500ms 的小赌注"。

Q15:门口都直接拒了,那还搞个 LIFO 干嘛?

水位线是个慢家伙(500ms 一拍),两拍之间的空窗期——突发流量涌入、或机器突然变慢——队伍会真实堆起来,堆的全是"有资格进门"的请求。LIFO 零延迟、无需计算,给反馈环的滞后兜底:空窗期里保证产能不喂废品。分工:门口水位线管"量"(放多少进来),队内 LIFO 管"序"(进来的谁先上座)。快层笨而即时(规则),慢层聪明而滞后(反馈环)——汽车的 ABS + 定速巡航同款分层。

Q16:是不是用 monitor 做 sampling 估算 processing speed,然后动态调节队列等待时间?

第一代连"估算"都不需要:阈值写死,但测的就是每个请求真实等了多久(进队盖时间戳,出队一减)——处理速度的变化自动灌进等待时间这个测量值,不需要算出这个中间量。能直接测量目标量,就绝不估算中间量(估算有模型误差、滞后、采样噪声;时间差精确实时免费)。"阈值本身也动起来"是第二代(P90)才做的事。

Q17:不过载的时候还是 FIFO?

是。平时所有聪明零件全部休眠:队列几乎空、等待接近零、t5 和 t1 得到一模一样的服务。优先级不是"贵客永远走快速通道"的常态特权,而是急诊分诊——大规模伤亡事件发生那一刻规则才启动。好的保护机制像保险丝:99.99% 的时间里唯一的工作是隐形;平时容量够用时,任何聪明的排序都是纯开销。

Q18:PID 公式他们自己想的?汽车巡航也是这个?

1922 年军舰自动舵,104 岁,九成工业控制回路是它;定速巡航是教科书案例(上坡=I 项攒账,坡顶过冲=integral windup)。Uber 的本事是识别同构:"测量量+旋钮+已知目标+单调+滞后" → 百年老解。目标已知用 PID(调节),目标未知用爬山(寻优)——N 属于后者。

Q19:auto-tuner 找到最优 N 之后,为什么不停下来?(TCP 那个"永不停的 +1")

因为山峰会挪:流量构成一变,最优 N 就漂移;你若在峰顶坐下不动,容量悄悄涨了你永远不知道,只能永远用着过时的答案。TCP 的解法是永不停止地 +1 试探——用"偶尔撞一次墙"(丢一个包/多拒几个请求)的小代价,持续购买"峰顶现在在哪"的实时情报。探测的成本,就是知识的价格。配上不对称的步长(上探 +1 蹑手蹑脚,撞墙 ×0.5 夺路而逃——因为两个方向的错误代价不对称),就是跑了四十年的 AIMD。这是整个"static → adaptive"故事的最纯粹形态:没有一劳永逸的正确配置,只有持续重新发现正确配置的机制。

Q20:优先级谁来定?我的想法:公司预定义 + 依赖树传播(Amazon tier 模型)。

对了一半:中央定义必须,但服务级标签在共享基础设施失效(同一个 Docstore 承载 t1 和 t5 流量)→ 升级为请求级标签沿调用链透传("为谁而做"而非"谁在执行")。防通胀靠给标签定价——Amazon 的 ORR/bar raising 正是价格的成熟实现,且"t1 的依赖也是 t1"在 ORR 下从福利下发变成连坐审查。

Q21:commit lag 和 Raft 啥关系?leader 限速了 follower 自然轻松啊?而且 leader 不就发发心跳和 AppendEntries?

quorum 故意剪断了"最慢 follower 反压 leader"的绳子(2/3 票即提交,不等最慢者)——快的代价是落后可以无声积累、冗余悄悄蒸发。leader 必须维护 matchIndex[](不记就没法数票定提交线;给不同 follower 发不同日志段这个行为本身就证明在逐个记位置),落后量是一个减法,信号免费。

2026-09-11 重读时的追问:

Q22:内部队列大小是多少?

文章没给,而且这是设计使然:CoDel 一族不用队列长度做控制量,用"已经等了多久"。长度和体验之间没有稳定关系(同样 100 个请求,机器快时 10ms 清空,慢时等 3 秒),等待时间才直接对应 caller 感受。实现上一般仍有一个上限防内存爆,但它是保险丝不是控制量。加上 rejector 在门口已按比例砍过,能进来的量本身就是"当前处理能力放得下"的。

Q23:threshold 是怎么动态调整的?"用旧 window 预测新 threshold"是什么意思?

它不是预测,是跟随。threshold = k × 最近 window 内实测的 P90 latency。第一性原理:arrival rate ≤ throughput 时一个请求最多等一个处理时间,等得更久就是积压;处理时间不是常数所以要测,能测到的只有已完成的请求。代价是 threshold 滞后真实情况一个 window:系统突变的头几秒按旧 threshold 判,是抖动就是误杀、是新常态就是正确的 fail fast,window 长度就是在赌这两者哪个更常见。我一开始把"多杀"说成了坏事,其实方向不定。

Q24:我记得 reject 是在 enqueue 之前发生的,和"等待超时"不矛盾吗?

我记对了,而且这是主力。Cinnamon 有两个 rejection point:rejector 在 enqueue 前按 PID 比例砍(绝大多数拒绝在这里),队列超时在 enqueue 后兜底(防放进来之后 throughput 掉了)。原文这篇没写清,是 2023 年 Cinnamon 系列博客的原句:"Next it enters the rejector that figures out whether we should reject the request or not... In cases where too many requests are queued,they will time out from the queue." 另外 PID 的输入在原系列里是队列的 inflow/outflow,不是延迟。

Q25:tier 0–5 是怎么参与工作的?rejector 也按 tier 拒吗?

是。PID 只给一个标量(砍多少),tier 把它变成确定性的决定(砍谁):rejector 统计最近各 tier 流量占比,从 t5 往上累加到比例为止,cutoff 落在某个 tier 内部;tier 内再按 caller hash 分 cohort,cutoff 落在哪一格那一格全拒,同一用户命运一致。队列本身也是按优先级 dequeue 的内存结构,只分读写两个。不按 tier 拒的只有 Scorecard,它按 tenant 配额拒。

Q26:enqueue 时的 rejection 和队列里的 timeout 逻辑不一样?PID 是不是维护两个 threshold?

不一样,而且 PID 只维护一个。Rejector 回答"接下来放多少、放谁",看整体 inflow/outflow,输出一条 tier cutoff,由 PID 驱动;timeout 回答"这一个请求是否已等太久",看它自己的到达时间 vs k × P90 latency,是统计跟随,没有反馈环。in-flight limit N 是第三个量,由 auto-tuner 管。我之前被本文"PID adjusts queue timeouts and inflight limits"一句带偏,说成 PID 输出两个量,已纠正。另外比例不是随机概率,是确定性的 cutoff。核对 Cinnamon 系列原文后,第 5 站环 1 写的"误差 = 等待时间差"也是错的,已在第 5 站顶部加更正。

Q27:什么时候切 LIFO?FIFO 模式和 tier 怎么一起工作?

tier 之间永远按优先级 dequeue,FIFO/LIFO 只在同一 tier 内部起作用。一代 CoDel 的切换判据是"window 内等得最少的请求也超过 target";Cinnamon 时代原文只说"under pressure it switches to LIFO",判据未写明,且门口 rejector 已控量,LIFO 的实际作用比一代小得多。

Q28:Scorecard 的上限是 queued 请求数吗?是按 P90 拒的吗?最新一代也有 static threshold?

上限是该 tenant 已接收未返回的请求数(排队中 + 执行中,原文未明确,按隔离目的推断)。与 P90 无关,P90 只参与队列 timeout 这一个地方。是的,Scorecard 的 quota 是三个 rejection point 里唯一静态的,而且是故意的:它管的是"谁能用多少"这个政策问题,不是"系统撑不撑得住"这个物理问题,政策只能配。见原则 16。

6. 与我自己经验的连接

  • Amazon load test(压到 knee):方法正确,产出是快照;knee 处的并发数才是跨场景稳定的不变量。下次可以验证:换流量构成重跑,TPS knee 会大挪、concurrency knee 基本不动。
  • OpenSearch plugin 事故:完整的 metastable failure 案例——plugin 抬高单请求成本(容量分母变了,所有按条数设的限全部失效)→ crash → 回滚无效(backlog+retry 自持回路)→ 新请求排在过期老请求后(FIFO 陷阱)→ 按年龄分流 DLQ 破局(手写 CoDel)。教训:给每条队列在设计之日配 TTL,预先切断自持回路。
  • Amazon tier/ORR 体系:治理层的成熟实现(给标签定价防通胀);Uber 文章补的是执行层(请求级透传)。两层拼起来才完整。

7. 通用原则清单(可移植到任何系统)

1. 决策放在信息所在地。远程守门永远在猜,干活的机器直接知道。全局计数难题往往可以靠重选执行点定义掉。
2. 选自我校准的量。concurrency 胜 TPS、等待时间胜队伍长度、P90 胜写死的 5ms、延迟膨胀率胜猜容量——每次二选一,赢的都是"机器变化自动灌进测量值"的那个。
3. 成本事前不可测时,按占用时长事后结算。并发槽自动给贵的请求收贵的费,不需要任何人预测成本。
4. 政策 constant,容量 adaptive。看到一个 limit 先问:这数字是合同还是容量估计?合同要恒定可解释,估计必须会自己动。
5. stateless 动容量(autoscale),stateful 动准入(adaptive shedding)。负载 ≤ 容量这个不等式,两边挑一边动;容量焊死时只剩左边。
6. Fail fast,别把请求捏在内存里。判得了的立刻判;backlog 是储存的需求,必然违约的债越滚越贵——每条队列设计之日就配 TTL。
7. 反馈不靠预测准取胜。靠误差有界 + 快速自愈 + 错了也安全。把"做对一个大预测"换成"快速迭代一万个 500ms 的小赌注"。
8. 能直接测量目标量,就不估算中间量。时间戳一减,胜过任何速度模型。
9. 错误代价不对称,步长就该不对称(AIMD)。朝危险方向蹑手蹑脚,朝安全方向夺路而逃;峰顶仍要 +1——探测成本是知识的价格。
10. 记仇的项配遗忘机制。积分/累计类状态必须会过期,否则病愈后旧账压着不放(integral windup)。
11. 快慢分层,环速错开。快层笨而零延迟(规则:LIFO/比大小),慢层聪明而有滞后(反馈环);两环速度接近必共振。
12. 只留一个决策脑,信号插件化。多个限流组件独立决策 = 脑裂;远程信息优先搭已有通信的便车(matchIndex),不新建上报系统。
13. 过载时,公平让位给存活价值最大化。牺牲不可避免时,"牺牲谁"必须是显式决定(优先级),不能交给随机时机。
14. 目标已知 → PID;目标未知 → 爬山。调节问题和寻优问题是两个物种,认错会翻车(单调性是 PID 的隐藏前提)。
16. 政策静态,感知动态。"系统现在撑不撑得住"是物理事实,只能测不能配(rejector / timeout / auto-tuner 全动态);"一个 tenant 最多能占多少"是人定的政策,没有物理量可测,只能配(Scorecard 静态)。一代之前静态配额的死因不是静态,而是住得离数据太远、成本模型失真、且是唯一保护层。
15. 软件规模大了就是物理系统。惯性、滞后、振荡、共振——处理它们的数学在隔壁自动化系躺了一百年,最聪明的一步是识别同构,不是发明新公式。
