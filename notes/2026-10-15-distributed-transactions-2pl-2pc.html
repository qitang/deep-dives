1. 读物总结

背景。课程前半段讲的是"多台机器装成一台可靠的机器"（Raft、ZooKeeper），从这篇起转向"多台机器各管一片数据，为了性能"。数据一分片，一个应用操作就可能跨多台机器：转账要改两个账户，建索引要同时写主表和索引表。两件事立刻冒出来：别的操作同时在跑怎么办（并发），做到一半有机器崩了怎么办（故障）。数据库在 1975 年（System R）就给了答案：transaction，程序员标出 BEGIN/END，系统自动提供好行为，概括成 ACID。这篇读物不是一篇论文，是 6.033 教材第 9 章 + 课程 notes + DDIA 的拼盘，讲 transaction 在单机和跨机器时各靠什么实现。

三个名字三件事。这是课程 notes 的主轴：distributed transaction = concurrency control + atomic commit。concurrency control 管 isolation（6.033 叫 before-or-after atomicity），工具是 2PL；atomic commit 管 atomicity（6.033 叫 all-or-nothing），工具是 2PC；再加上前几篇的 replication，工具是 Raft。三个独立的问题，三个独立的工具，一个真实的分布式数据库三个都要装（Spanner）。

Isolation 有几档。DDIA 第 7 章的阶梯：read committed（只读已提交的、只覆盖已提交的，挡 dirty read / dirty write）→ snapshot isolation（整个事务看开始那一刻的世界，挡 read skew，Postgres 叫 repeatable read，用 MVCC 实现，读不加锁）→ serializable（结果等于某一种串行顺序，挡所有异常，包括 lost update、write skew、phantom）。三档的写锁一模一样（exclusive，攥到 COMMIT），差别全在读那一列。serializable 的实现有三条路：真串行（VoltDB、Redis）、2PL（三十年来唯一的路）、SSI（Postgres 9.1+，乐观地跑、提交时查前提）。

2PL。6.033 §9.5 给了三种用锁的纪律，一种比一种并发高：全局一把锁；simple locking（事务开始时报出所有要碰的行一次锁齐，到 lock point 后放）；two-phase locking（用到哪行才锁哪行，但一把都不许提前放，COMMIT 或 ABORT 时一起放，锁数先单调涨后单调降，所以叫两阶段）。2PL 比 simple locking 并发高的场景是"事务要碰哪些行取决于它先读到什么"。不能早放的理由：别人会看到半成品，或者看到一个将被回滚的值。代价一：读也要加 shared lock，和 snapshot isolation 的"读写互不阻塞"是根本分叉。代价二：deadlock 是必然副作用，治法四种（锁排序、超时、找环、wound-wait），外加随机退避防 livelock。

2PC。6.033 §9.6.3 和课程 notes 的协议：coordinator（TC）给每个 participant 发 PREPARE；participant 把暂存值和"我投了 YES"先写盘再回 YES，从此不能单方面反悔；TC 收齐 YES 后写盘 COMMIT（这一行是不可撤销的那一刻），再发 COMMIT 消息；participant 转正、放锁、回 ACK。N 个 participant 共 3N 条消息。崩溃分析：participant 在 YES 之前崩 → 忘掉；YES 之后崩 → 恢复暂存、重拿锁、问 TC；COMMIT 之后崩 → 用 TID 去重再 ACK。TC 在写盘 COMMIT 之前崩 → 重启查无记录一律 ABORT（presumed abort）；之后崩 → 重发 COMMIT。

阻塞问题的根。participant 回了 YES 后 TC 失联，它既不能 ABORT（TC 可能已让别人 COMMIT）也不能 COMMIT（别人可能投了 NO 或 TC 还没写盘）。两个坏世界在 participant 眼里收到的消息序列完全相同，所以它手里的信息不够做任何决定，只能攥着锁等。超时不帮忙。3PC 多插一轮 PRE-COMMIT 想换掉阻塞，但需要完美故障检测器（分清"TC 死了"和"网络断了"），真实网络没有，所以没人用。两将军问题和 2PC 的关系：2PC 不解决它也不需要解决它，因为 2PC 只有一个决策者，而且不要求同时（eventually 不是 simultaneously）。

两组对照。2PC 要全体同意、Raft 只要多数派：Raft 里一台机器可替（别人有一样的），2PC 里一个 participant 不可替（y 只有 B 有）；Raft 为可用性而生，2PC 对可用性零贡献反而放大故障。serializable vs linearizable：都是"等于某个串行顺序"，差别是 linearizable 多了"该顺序和真实时间一致"并且对象是单个操作而不是事务；一个 snapshot isolation 的只读事务可以 serializable 但不 linearizable。

落地。把 TC 和 participant 各自用 Raft 复制起来再跑 2PC（Spanner 的结构）：解决了等的时长、单盘单机；没解决阻塞的结构、全体同意、更慢。Kafka 事务就是 2PC：transaction coordinator 写 PREPARE_COMMIT 到 __transaction_state，partition leader 是 participant，COMMIT marker 代替 COMMIT 消息，省掉了 PREPARE 轮（participant 永远 YES），没有写锁（追加不覆盖），阻塞转移到 read_committed 的 consumer 身上。outbox 模式不做 2PC，用本地事务 + 异步投递绕开它，放弃同时可见、恰好一次、跨系统 abort，换来无锁、无 in-doubt、故障隔离。

2. 核心争论：no dirty write 到底防什么

这篇最长的一段卡在一个看起来最基础的地方：read committed 的两条规则里，"不读未提交的"（no dirty read）我一直懂，"不覆盖未提交的"（no dirty write）我好几年没搞清楚它防的是什么。这次跑了十几轮，我说了"你有点 hallucination 了"和"你先想清楚再讲"各一次，最后通了。推导链整理如下，包括讲的人走过的弯路，因为弯路本身说明了这个概念为什么难。

1. 问题的形状。T1 把 x 写成 1，没 COMMIT。T2 把 x 写成 2，COMMIT 了。允许这个发生，到底坏在哪？如果 T1 最后也 COMMIT，x = 2，等于串行 T1→T2，什么都不坏。这一点要先承认，不承认就一直对不上。

2. 弯路一：undo log 的画面。老式数据库 ABORT = 把 x 恢复成"我写之前的值"。T1 小本子记着"x 原来是 0"，ABORT 时盲目写回 0，把 T2 已提交的 2 抹掉了。这个理由我认可，但追问：MVCC 下还成立吗？不成立，MVCC 的 ABORT 没有写回动作。讲的人把 undo 的画面硬套到了 MVCC 上。

3. 弯路二：拿 lost update 当例子。两个事务都读 x=10 再各写回 11 和 15，T1 的 +1 丢了。我指出：这是 lost update，不是 dirty write，而且 read committed 明说不治 lost update。对。

4. 弯路三：DDIA 的二手车例子。Alice 和 Bob 各写两行（车卖给谁、发票开给谁），两组写穿插，结果车归 Bob 发票寄 Alice。例子对，但我说"很绕"，因为它展示的是后果不是机制。

5. 通的版本（MVCC 下的机制）。我自己的话：

no dirty write 就是 MVCC 的情况。每个 update 其实是一个 delete 和 insert。如果允许 dirty write，而且这个 write 是个 update，然后这个 update 之后又没 update 了，然后第一个 update 最后被 cancel 了，就会导致一个 delete 和 insert 都被 cancel，这样 MVCC 就有两个 version 是 visible 的。

展开：T1（txid 13）写 x=1 → v0 标 deleted_by=13，挂 v1 created_by=13。T2（14）不等，只能把它看到的最新版本 v1 标 deleted_by=14，挂 v2。T1 ABORT → 13 的一切作废：对 v0 的删除不算数，v0 复活；v1 的创建不算数。T2 COMMIT → v2 可见。结果 v0 和 v2 对同一个读者同时可见，SELECT x 返回两行。这不是"存了多个版本"（MVCC 的常态，供不同快照的读者各取一个），是"链断成两条，没人负责 v0"。T2 写的时候不知道该不该连 v0 一起删，因为 T1 的结局还没出来。

6. 根本理由（不依赖实现）。绝大多数写是读改写（x = x + 5）。T2 的新值要从一个前驱算出来，T1 不出结局，前驱是 0 还是 1 就不知道，15 和 16 只能蒙一个，而且 T2 没有任何信息能让它选对，因为答案依赖一个未来事件。所以第二个写者等第一个出结局。undo log、MVCC 只是各家数据库用来"等"和"恢复"的机械，机械不是理由。

7. 结论分三条。纯盲写且都 COMMIT：不坏。纯盲写且 T1 ABORT：MVCC 出两个可见版本，坏；理论上能靠多标一个删除修掉，Postgres 没这么做。读改写：任何实现都必须等。写锁攥到 COMMIT 一条规则三类情况全治，所以三档隔离级别的写锁一模一样。

教训（给讲的人）：我质疑实现细节时几乎都对；要把"机制"和"理由"分开讲，先承认无害的分支，再指出有害的分支。

3. 七站机制拆解

第 1 站 · 三个坏场景，三个名字

x = y = 10。T1 转账（x+1, y−1），T2 审计（读 x、读 y、打印）。合法结果只有 11,9（T1 先）和 10,10（T2 先）。

坏场景 ①（交错）                                       → isolation，工具 2PL
T1:  r(x)=10  w(x)=11                       r(y)=10  w(y)=9  COMMIT
T2:                    r(x)=11  r(y)=10  打印 11,10   ← 21 块，不是任何串行结果

坏场景 ②（半截，x、y 在两台机器）                        → atomicity，工具 2PC
x 机:  w(x)=11  COMMIT
y 机:  ✗
数据: x=11 y=10（永久）

坏场景 ③（没了，x 那台彻底挂）                           → replication，工具 Raft

serializable 的定义从场景 ① 长出来：并发跑完的结果等于某一种串行顺序的结果就算对，哪一种不管。这和 linearizable 的差别留到第 6 站。

第 2 站 · 隔离级别阶梯

级别挡住漏掉实现
read committeddirty read、dirty writeread skew、lost update、write skew写锁到 COMMIT；读不锁，走版本链拿旧的已提交值，每条语句一张快照
snapshot isolation
（Postgres 叫 repeatable read）		+ read skew、（Postgres）lost updatewrite skew、phantom写锁同上；读不锁，整个事务一张快照（MVCC：txid 比我大的或我开始时没提交的版本不看）
serializable全部—2PL（读也加 shared lock）/ SSI / 真串行

read skew：T2 的两次读跨在 T1 的提交线两边，读到 10 和 9，少 1 块。ZooKeeper 的 fuzzy snapshot 就是它，ZK 不修靠幂等重放收敛，数据库要修因为快照给人读。lost update：两个事务都读 42 各写 43，一个 +1 丢了；三种修法：原子写（SET v = v + 1）、SELECT FOR UPDATE、Postgres RR 自动检测"你改的版本被人盖过"abort 之。write skew：两个医生都读到 2 人在班，各改自己那行，都提交，0 人在班；两个事务写不同的行，lost update 检测抓不到，病根在读的前提被改。phantom：前提是"不存在这样的行"（会议室预订查到 0 行），写入凭空造出一行改变别人的查询结果，没有行可锁，要 predicate lock / index-range lock 或 SSI。

repeatable read 的 "repeatable"：同一事务同一行读两遍一样，名字从它禁的异常 non-repeatable read 反过来起的。快照隔离给的比名字多（所有行冻在同一刻）。

第 3 站 · 2PL

画法（这篇最后定下的）：严格一步一行，左边谁干什么，中间每个数据的"格子里是谁的名字"，右边数据当前值。

两条规则。A 拿：碰一行之前先在它的格子写名字，格子有人就等。B 放：写上的名字一个都不许提前擦，COMMIT 或 ABORT 时全部一起擦。

                      x 的格子    y 的格子
开始                    空          空
第 1 步 读 x            T1          空      ← 用到才拿（simple locking 这一行就是 T1 T1）
第 2 步 写 x = 11       T1          空
第 3 步 读 y            T1          T1      ← 现在才碰 y
第 4 步 写 y = 9        T1          T1
第 5 步 COMMIT          空          空      ← 一起擦

第 2 步之后 x=11 y=10 这个错的中间状态真实存在（6.033 §9.1.6：中间状态可以错，只要没人能看见）。T2 想看两半：先读 x → 排队到 T1 COMMIT；先读 y → T2 名字留在 y 格子，T1 第 3 步被拦 → deadlock → 杀一个重来。

为什么不能早放（规则 B）：T1 写完 x 擦掉名字，T2 读 x=1 写 z，COMMIT；T1 再写 y 或 ABORT。两个坏场景：T1 ABORT 则 z 抄了一个从没存在过的值；T1 不 ABORT 则 z = 1 + 0 = 1，不是任何串行结果（0 或 2）。病根：T1 擦名字时它的事没办完。

锁的两种颜色。读拿 shared（可以多个读者一起，等写者）；写拿 exclusive（等所有人）。读锁的用途：把"我读到的前提"钉住，别人在我提交前不能改它。用 2PL 跑医生例子：两人都拿 shared，都想升级 exclusive → deadlock → 杀一个 → 重跑读到 1 被拒。read committed / snapshot isolation 的读根本不看格子，这是和 2PL 的分界。

Deadlock：2PL 允许边跑边拿，就不能保证拿的顺序一致，闭环不可避免。四招：锁排序（预防，但要提前知道锁集）、超时、找环（Postgres/MySQL）、wound-wait（老杀新，Spanner）。serializable 下 deadlock 比 read committed 频繁得多，因为读也留名，能互相拦的动作多了。两个事务都"读 x 再写 x"，一行数据就能死锁（升级锁）。livelock 用随机指数退避。

官方题（2PL 比 simple locking 性能好的场景）：T1 先碰 x 再碰 y，T2 只碰 y，T2 在 T1 刚锁 x 时到达；simple locking 下 T2 等，2PL 下 T2 不等。一般形式：事务要碰哪些行取决于它先读到什么。

第 4 站 · 2PC 协议与逐步崩溃

步骤                             TC                   A（管 x）              B（管 y）
1  TC 分配 TID = 7
2  TC 发 put 给 A、B                                  拿 x 锁，暂存 11         拿 y 锁，暂存 9
3  应用说 END
4  TC → A、B：PREPARE(7)
5                                                    写盘 PREPARED，回 YES    写盘 PREPARED，回 YES
6  TC 收齐 YES，写盘 "7 COMMIT"   ← 结局定了，不可撤销
7  TC → A、B：COMMIT(7)
8                                                    11 转正，放锁，回 ACK    9 转正，放锁，回 ACK
9  TC 收齐 ACK，忘掉 7

第 2 行拿的锁到第 8 行才放，跨两轮网络往返和三次写盘，这是 2PC 慢和 deadlock 范围扩大的原因。

第 5 行写盘的意义：没写盘就回 YES，B 崩了重启，暂存的 9 没了，TC 发 COMMIT 它做不了，A 已经加了钱，x=11 y=10 永久。写盘让 YES 的承诺崩溃后还能兑现。

B 崩在磁盘上有什么重启后安全的理由
第 5 行之前没有 7忘掉；之后 PREPARE 来了回 NO没回过 YES，TC 不可能 COMMIT
第 5 行之后、第 7 行之前PREPARED, y=9恢复暂存、重拿 y 锁、问 TC 结局YES 可能已送达，A 可能已提交
第 8 行之后y=9 已转正收到重复 COMMIT 再 ACKTID + 状态记录造出的至多一次
TC 崩在重启后安全的理由
第 6 行之前查无 COMMIT 记录 → ABORT（presumed abort）没写盘就不可能发过 COMMIT，A、B 谁都没提交
第 6 行之后重发 COMMIT决定在磁盘上，照着执行

谁 trigger 那个 ABORT：TC 扫日志找"有开始没 COMMIT"的；或 B 作为 persistent sender 追问，TC 查无记录回 ABORT。B 回完 ACK 可以彻底忘掉 7，之后迟到的 COMMIT(7) 查无此事务 = 已做完，直接 ACK；成立的前提是 PREPARED 永远写在 YES 之前。

第 5 站（心脏站）· 阻塞问题的根

B 写盘 PREPARED、回了 YES，TC 不回话。两个选择，各有一个让它出错的世界：

选择 1：B 自己 ABORT 的坏世界            选择 2：B 自己 COMMIT 的坏世界
A：YES                                   A：NO（x 账户被冻结）
B：YES                                   B：YES
TC：写盘 COMMIT，发给 A，发给 B 前崩 ✗     TC：写盘 ABORT，发给 A，发给 B 前崩 ✗
A：提交                                  A：回滚
B：ABORT → x=11 y=10                     B：COMMIT → x=10 y=9

从 B 的视角两个世界收到的消息序列完全相同："我投了 YES，然后没消息了"。不管选哪边都有一个世界让它错。超时不帮忙，等再久信息也不多一个比特。唯一不出错的动作是攥着锁等。投出 YES 的那一刻 B 把决定权交出去了，换来"TC 说 COMMIT 我一定能做到"这个承诺。

B 去问 A：A 说"我投 NO"→ ABORT 行；A 说"我已 COMMIT"→ COMMIT 行；A 说"我也 YES 也在等"→ 还是两个世界。3PC 在 YES 和 COMMIT 之间插一轮 PRE-COMMIT，使"收到 PRE-COMMIT ⇒ 所有人 YES"、"有人 COMMIT ⇒ 所有人收到 PRE-COMMIT"，TC 崩了 participant 互问就能定。但它建立在"TC 真的死了"上，而判死只有超时，分不清 TC 崩了和网络断了：{TC, A} | {B} 分区，B 没收到 PRE-COMMIT 认定 TC 死 → ABORT，TC 那边收到 A 的 ACK → COMMIT。需要完美故障检测器，真实网络没有。两将军：必须同时进攻、信使会丢，有限条消息做不到（最后一条可能丢所以多余，归纳到零）。2PC 不碰它：单决策者（TC 不会跟自己打架）+ 无同时性要求（eventually 不是 simultaneously）。不是拜占庭将军（那是人撒谎，PBFT 第 16 篇）。

第 6 站 · 两组对照

Raft 里的一台 server2PC 里的一个 participant
它干的活和其他人一模一样和其他人不一样（A 管 x，B 管 y）
少了它别人有一样的，可替没人有 y，不可替
需要几个同意多数派（多数派里必有最新的，两个多数派必相交）全体
误判对方死了多一轮选举，不出错一边有一边没有
对可用性为它而生，5 挂 2 照常零贡献，3 挂 1 全停，放大故障
serializablelinearizable
对象事务（多操作、多行）单个操作、单个 key
要求存在某个串行顺序结果一样同左，且该顺序和真实时间一致
出处数据库圈分布式圈（Herlihy & Wing 1990，原本讲单机多线程共享对象）

两条独立的轴（我的总结："一个是 transaction，一个是 consistency"）。三种组合：snapshot isolation 的只读事务（S 不 L）；Raft 上的 KV（L 不 S）；Spanner 的 external consistency = strict serializability（都有）。S 不 L 的单机例子：T2 BEGIN(repeatable read) → T1 UPDATE x=11 COMMIT → T2 SELECT x 读到 10。T2 开始得早、读发生得晚；serializable 认（T2 排前面说得通），linearizable 不认（墙上钟 T1 在前）。多副本版：T1 在 primary 提交，T2 在落后的 replica 读到 10。两个版本共同点：这次读在真实时间上晚于 T1 的提交却读到旧值。

第 7 站 · 落地

TC 用 Raft 复制：第 4 站第 6 行"写盘 COMMIT"变成"复制到多数派"。解决了：等的时间从修机器缩到选 leader、单盘坏不丢、单机崩不停。没解决：阻塞的结构（B 的信息不足是 cp1 的结论，复制不给它多一个比特）、全体同意（一个 group 多数派不在就停）、更慢（三次写盘各变一轮复制）。口算：TC leader 在 COMMIT 复制到多数派前崩，新 leader log 里没有 → ABORT，= presumed abort。这就是 Spanner 的结构。

它就是那个"serializable 但不 linearizable"的例子本身：T2 开始早、读发生晚、读到旧值。syllabus 给 4(a) 的提示"只读事务读旧快照"说的就是这个。replica 例子是同一回事的另一种来源：一个是时间上的旧（快照冻住），一个是空间上的旧（副本落后）。

repeatable read 涉及到一个 transaction 里面的多个 read，一个 read 到 old 一个 read 到 new 的？

反了。一旧一新叫 non-repeatable read，是 read committed 的病；repeatable read 的名字就是把它禁掉，所以全旧。"全旧"正是 4(a) 要的东西：T1 已提交 11，T2 还在读 10。

"repeatable read 全旧"这是为什么呢？因为 2PL？

不是 2PL，是 MVCC 的快照规则：T2 txid 12，T1 txid 13 创建的 x=11，13 > 12 永远成立，T2 活多久都看不到 11。对比两种实现 repeatable 的办法：MVCC 让写者绕开读者（读旧版本），2PL 让写者等读者（shared lock 攥到 COMMIT，DB2）。Postgres 是前者，所以是"读不到最新"而不是"别人改不了"。

MVCC 这个我懂，但是前提是我的 T2 read 是在 T1 开始之前啊。

前提正确，是 T2 必须在 T1 提交之前开始（不然 txid 更大能看到 11）。但 T2 的读在 T1 提交之后。linearizable 看的是操作（这次读）的时间，不是事务开始时间。事务开始得早、读发生得晚，两个标准看的粒度不同在这里分岔。

但是你刚刚这么说的：T1 write and commit, and then T2 read。

抓对了。讲的人之前说"T1 提交后一秒 T2 才开始"，这在单机 Postgres 上不成立（T2 txid 更大直接读到 11），只在多副本下成立（replica 落后）。4(a) 有两个成立的版本：单机 SI（T2 开始 → T1 写提交 → T2 读到 10）和多副本（T1 写提交 → T2 在 replica 开始并读到 10），共同点是这次读在真实时间上晚于 T1 的提交却读到旧值。

有点意思，这和 transaction 完全没关系了啊，你这是分布式系统的范畴了，你在这讲 serializable 是啥意思？

这题就是让我拿一个例子证明它们是两个范畴。课程 notes 定义 serializable 时写了"this should remind you of linearizability"，学生总以为 serializable 比 linearizable 强，这题把这个误解打掉：serializable 一点都不管时间，所以一个 serializable 的系统照样可以返回陈旧数据。单机版就够回答这题，replica 版是讲的人多扯的。

我的理解：从理论上说聊 serializable 或者 transaction 都是 assume request 打到同一个 host，data 只有一个副本（同一版本号，可以有多版本）；说 consistency 是讨论 multiple hosts 一个数据多个副本。这完全不是同一个东西和框架，你让我怎么比较？

划分基本对，就是 FAQ 那段话的意思（两个词出自两个圈子）。题目不是要比较谁强，要的只有一句：serializable 的定义里没有真实时间。这个性质不需要多副本就能看出来。划分里唯一要修的地方：linearizable 在单机上也有意义，只有一份数据、多个版本，照样可以不 linearizable。

linearizable 是说 linearizable consistency 吗？

同一个东西，= linearizability，Raft 和 ZooKeeper 那两篇的主角。这篇里它只客串一次。

单机谈什么 linearizable？

定义里没有"副本"这个词：每个操作要么全在另一个之前要么全在之后，且先后和墙上钟一致。Herlihy & Wing 1990 提出它时讨论的是单机多线程共享对象（一个 queue 被几个线程 push/pop），分布式后来借用。单机两类东西可以不 linearizable：多线程下的数据结构（A increment 返回了 B 读到 CPU cache 里的旧值，volatile 和 memory barrier 解决的事）；数据库的 snapshot isolation。形状一样：一个写已完成并返回，一个之后发起的读却没看到它。

"一个写已经完成并返回，一个之后发起的读却没看到它"，这个在单机版的 Postgres 上面也不会发生吧？

会，条件是读所在的事务开始得早：T2 BEGIN(repeatable read) → T1 UPDATE x=11 COMMIT（写完成返回）→ T2 SELECT x 读到 10（之后发起的读）。Postgres 文档明写：RR 事务看第一条语句执行时的快照，之后的提交一律不可见。直觉"单机不会发生"是把事务当成了一个瞬间。单机 Postgres 的单条语句是 linearizable 的，RR 事务里的后续读不是。

所以 Postgres allow begin a transaction 然后 sleep for 10 mins 然后 do select 然后 commit？就是 transaction 里面掺 application logic？

允许，不限事务时长。DDIA："传统关系数据库不限制事务持续时间，因为它们是为等待人类输入的交互式应用设计的。"这正是 snapshot isolation 存在的理由：长事务（备份、报表）要看一个冻住的世界。代价：旧版本不能 vacuum、锁不放、idle in transaction 占连接池。事务尽量短是惯例不是限制。

复述其他

（cp4b）phantom write。

名字接近但不是。syllabus 要的异常叫 write skew。关系：write skew 是病（读一个前提、基于它写别处、前提在提交前被改），phantom 是让这个病更难治的一种诱因（别人新插入/删除的行改变了我的查询结果集，没有行可锁）。医生例子不是 phantom（被改的是已存在的行，SELECT FOR UPDATE 能挡），会议室预订才是。

5. 与我自己经验的连接

  • pump.fun 的 Postgres 默认 read committed。读不加锁走版本链、写加 exclusive lock 到 COMMIT。两个 UPDATE 互相等、lock_timeout 触发，就是那把写锁。只读查询永远不参与 deadlock。
  • 读写分离的 replica = checkpoint 4(a) 的多副本版。primary 提交了，应用去 replica 读到旧值，serializable 认、linearizable 不认。
  • Postgres 允许事务里掺 application logic、跨网络请求。长事务的代价（vacuum 不了、锁不放、idle in transaction 占连接池）我在生产见过。
  • Kafka 事务 = 2PC：__transaction_state 是 TC 的日志，partition leader 是 participant，COMMIT marker 是 COMMIT 消息。省掉 PREPARE 轮因为 participant 永远 YES；没有写锁因为追加不覆盖；阻塞落在 read_committed consumer 的 LSO 上。Kafka idempotent producer 的 sequence number 去重 = 2PC 的 TID 去重 = Raft §8。
  • outbox 我经常用。这次说清了它放弃的三样（同时可见、恰好一次、跨系统 abort）和换来的（无锁、无 in-doubt、故障隔离）。判断要不要真 2PC 的一条线：第二个系统有权说 NO 且业务不能忍补偿窗口。
  • ZooKeeper 第 5 站的 fuzzy snapshot = read skew，这篇第 2 站从这里接上。ZK 不修靠幂等重放，数据库修靠 snapshot isolation，差别在快照给不给人读。
  • ZooKeeper 第 7 站 fencing 的 lost update（不加 last_token 条件，A 的过期计算盖掉 B 的）和这篇第 2 站幕 3 的 lost update 是同一个病，那时是跨进程 GC 暂停，这里是两个并发事务。
  • Raft term / ZK epoch / Kafka epoch / fencing token / 2PC 的 TID：单调号让迟到的旧东西被认出来。六周收尾那张表再加一列。

6. 通用原则清单

  1. 三个名字三件事，别混。2PL 管 isolation，2PC 管 atomicity，Raft 管 replication；一个真实系统三个都装，谁也替不了谁。
  2. 往上爬一档隔离级别，写锁从来不动，只动读那一列。read committed、snapshot isolation、serializable 的写锁一模一样（exclusive 到 COMMIT）；差别全在读返回哪个版本、读要不要留名。
  3. 第二个写者等第一个出结局，因为它的新值要从前驱算出来，而前驱是哪个取决于一个未来事件。undo log、MVCC 只是"等"和"恢复"的机械，机械不是理由。
  4. 中间状态可以错，只要没人能看见。锁攥到 COMMIT 不是为了让中间状态不存在，是为了让想看两半的人要么排队要么撞 deadlock 重来。
  5. 读锁钉住前提。基于读到的东西做决定、决定要写到别处，前提在提交前被改就是 write skew；只有把前提锁住（2PL）或提交时查前提（SSI）才挡得住，快照隔离挡不住。
  6. "同时"不是分布式系统能承诺的，"最终"才是。锁先后放无所谓，只要结局定下来之前一个都不放；2PC 保证 eventually 不是 simultaneously，这一点放松让它从两将军的不可能变成可能。
  7. 承诺之前先落盘。participant 回 YES 前写 PREPARED，TC 发 COMMIT 前写 COMMIT；写盘的那一刻就是不可撤销的那一刻，崩溃后靠它兑现承诺。
  8. 查无此事务 = ABORT（对 TC）或 = 已做完（对 participant）。两条推理成立的前提都是"落盘永远在发消息之前"，规则互相咬合。
  9. 投出 YES 就交出了决定权。之后两个坏世界在你眼里消息序列相同，信息不够做任何决定，超时不增加信息；想不等就要完美判死，真实网络没有。
  10. 可替的东西要多数派，不可替的东西要全体。Raft 的 server 可替所以多数派够、误判不出错、为可用性而生；2PC 的 participant 不可替所以要全体、误判就出错、放大故障。
  11. serializable 的定义里没有时间。一个 serializable 的系统照样可以返回陈旧数据；要"读到最新"得另加 linearizable，两个都要叫 strict serializability。
  12. linearizable 不是多副本专属。"一个写完成并返回、一个之后发起的读没看到它"在单机多线程和单机 snapshot isolation 下都会发生。
  13. 追加不覆盖，就不需要写锁。Kafka 的 participant 永远 YES、没有写锁，阻塞转移到要求"已提交 + 按序"的读者身上。
  14. 绕开 2PC 的条件是第二个系统无权说 NO。outbox 用本地事务 + 异步投递换掉锁和 in-doubt；第二方可能拒绝且业务不能忍补偿窗口时，绕不开。

7. 复述结果与回忆清单

道考点结果
1YES 之后能不能单方面决定实。结论秒答；坏世界要追问三次才凑齐（漏了 A 投 NO 那个最直接的）；共同点说"看不到全貌"，补了"消息序列相同"
2全体 vs 多数派实。replica 做同一件事 vs 各做各的，追一步就推到"任何一个挂了都不行"
32PL vs simple locking 例子半实。deadlock 秒答；例子要架子（"T1 碰 x 再 y，T2 只碰 y"）才填出来；中间岔出去担心 reader 读到中间态，规则 B 堵死
4aserializable 不 linearizable通了，绕 10 轮。根因是"serializable 定义里没有时间"一开始不接受；讲的人第一版例子在单机不成立被我抓出来
4bSI 出 serializable 不出的异常半实。名字先说成 phantom，场景会讲，"为什么 SI 抓不到"没主动说
5Raft 复制 TC半实。"没法解决只是降低概率"对、"全体同意还在"追问后对；阻塞的根归到了 availability 没接到 cp1 的信息不足上

虚的三处有一个共同点："X 的定义里到底有什么、没有什么"这种边界问题。serializable 没有时间、write skew 不等于 phantom、阻塞的根是信息不是可用性。实的两道都是"坏场景推规则"，这个一向擅长。
