1. 论文总结

背景。Google 的广告后端 F1 原本跑在手工分片的 MySQL 上，最后一次重新分片花了两年。它要的东西三样都要：跨数据中心同步复制（一个机房挂了还能用）、跨分片事务（改两个账户要原子）、强一致读（改完密码别人立刻看到）。Bigtable 没有跨行事务，Megastore 有但写吞吐差。Spanner 是 2012 年给出的答案，第一个全球规模的、支持 externally consistent 分布式事务的数据库。

结构。数据切成几百上千片（tablet），每片一个 Paxos group（论文层面等价于一个 Raft 集群），副本跨数据中心。每个 group 的 leader 上有一张 lock table（2PL）和一个 transaction manager（2PC）。只碰一片的事务不需要 2PC；跨片的读写事务跑 2PC，coordinator 是参与的 group 之一的 leader，participant 和 coordinator 的状态都写进各自的 Paxos log，所以单机崩不再是阻塞点。这就是上一篇第 7 站画的"TC 和 participant 都用 Raft 复制"的实物。F1 的生产数据（Table 6）：读是写的 300 倍，延迟差 10 倍。整篇论文的聪明劲全花在只读事务上。

要解决的问题。一个只读事务要跨几片读到同一时刻的数据，不然就是 read skew。"同一时刻"需要一个所有片都认的数。Raft 的 log index 只在一个 group 内有意义，A 的 500 和 B 的 300 没法比；全局一个发号器（zxid 的做法）跨洲每次写都要领号，死路。只剩物理时间：东京的 10:00:00.005 和纽约的 10:00:00.003 直接可比。但物理时钟不准，两台机器差几毫秒是常态，直接用读数当戳会倒：先完成的拿到更大的数。Snowflake ID 就是这个毛病。

TrueTime。时钟不返回一个点，返回区间 [earliest, latest]，唯一承诺：真实时间在区间里。区间半宽 ε 来自三项：本地石英钟漂移（按最坏 200 µs/s 算，每 30 秒和 time master 对一次表，所以最多积 6 ms）、和 master 通信的延迟（约 1 ms）、master 自己的不确定。ε 是锯齿形，1 到 7 ms，平均 4 ms。time master 两种：GPS 和原子钟，失败模式不相关；每台机器问多个 master，用 Marzullo 算法剔除撒谎的；实测漂移超限的机器被踢出。TT.after(t) = 区间整个在 t 右边，t 一定过去了；TT.before(t) = 区间整个在 t 左边。TT.now() 不是网络调用，是本机读表加漂移上限，微秒级。

读写事务的两条规则（§4.1.2）。Start rule：coordinator 收到 commit 请求后调 TT.now()，取 latest 当 commit 戳 s，保证 s 不比"现在"小。Commit Wait：拿到 s 后不回复客户端、不放锁，等到 TT.after(s) 为真，保证回复时 s 已成"过去"。五行证明：s₁ < T1 完成时刻 < T2 开始时刻 ≤ T2 到服务器时刻 ≤ s₂。两条规则各管一头：取 latest 让我看见所有前人，等让所有后人看见我。代价每次写等约 2ε，和 Paxos 复制并行，Table 3 里关掉 commit wait 9.4 ms、开着 14.4 ms。

只读事务（§4.1.3–4.1.4）。开始时取一次 TT.now().latest 当 s_read，不等，不加锁，去本地副本按 snapshot isolation 读戳 ≤ s_read 的最新版本。副本可能落后，所以每个副本维护 t_safe = 已 apply 的最后一条写的戳，读的 s_read ≤ t_safe 才答，否则等。t_safe 成立靠两条前提：leader 发戳随 log 顺序单调涨（Spanner 加的规则），follower 按 log 顺序 apply（Raft 原有）。t_safe 还有第二个分量：group 里有投了 YES 没结局的 2PC 事务 T 时，t_safe 不能超过 T 的 prepare 戳减一，因为 T 的最终戳可能落在读的范围里。两种卡住：group 空闲（leader 每 8 秒发 MinNextTS 承诺"下一条写的戳 ≥ N"，副本推 t_safe 到 N−1）、in-doubt 事务（按 key range 细分）。单 group 的只读事务用 leader 的 LastTS 代替 TT.now().latest，省掉等"未来的写"，只等复制。

假设破了（§5.3 和 notes）。ε 变大只影响快慢：写多等 2ε，读等 t_safe 追上，正确性不变。区间不包住真实时间才出错：时钟太快，写事务提前结束 commit wait，戳在未来，之后开始的读看不见它；时钟太慢，戳偏小，和之前正常的写倒。两种都是安静地返回错值，没有报错。Google 敢这么做是因为三层检测把时钟故障率压到比坏 CPU 低 6 倍。这是本课第一个把 safety（不只是 liveness）押在物理世界假设上的系统。

结果。Table 3：写 14.4 ms，只读事务 1.4 ms，snapshot read 1.3 ms，只读是写的十分之一。Table 4：2PC 到 50 个 participant 延迟还平，100 个开始涨。Table 6（F1 24 小时）：读 8.7 ms、单片提交 72 ms、跨片提交 103 ms。F1 用 5 个副本（美国东西海岸），failover 对他们"几乎不可见"。CockroachDB 用 HLC 和不确定区重试近似这个设计，没有 TrueTime 所以只到 serializable；AWS DSQL 用 ClockBound 拿了 TrueTime 那一块，把 2PL+2PC 换成 OCC。

论文自己的教训（§8）。linchpin 是 TrueTime：把时钟不确定性作为 API 的返回值暴露出来，上层就能建更强的时间语义；底层把 ε 压得越小，上层付的代价越低。"作为一个社区，我们不该再依赖松散同步的时钟和弱时间 API 来设计分布式算法。"

2. 我定的三个词

第 5 站绕了几十轮，根因是"时间"一个词被三样东西共用。我在 2026-10-20 定了三个词，之后全篇用它们：

我的词符号论文的词是什么谁知道
selected timestampscommit timestamp s_i / s_read事务从 TT.now() 的区间里挑的那个数，写死在版本上（x@10=9 的 10）事务自己；写进数据后所有人
real-world timestamptt_abs(e)某个事件发生那一瞬间的真实时间没人精确知道，只知道在区间里

三者关系只有两条，都是写事务的：挑戳时 s ≥ t（取 latest，latest ≥ t）；完成时 s < c（等到 TT.after(s) 才回复）。读事务只有第一条，没有 c。

两个必须分开的东西：TT.now() 的区间（时钟不确定性，宽几毫秒，没人知道真实时间在哪一点）和 linearizability 的区间（一次操作从调用到返回，client 自己知道）。两个都写成一对数字，混了就全乱。还有一个：戳是标签不是测量值。T1 用 .010 做戳，真实发生的时刻不知道，只知道 ≤ .010；标签不精确，但标签的先后和真实先后一致，这是 Spanner 要的全部。

3. 核心争论：读事务之间的戳倒了为什么没事

这篇最长的一条链。起点是我质疑"读事务不用 commit wait 是因为没人需要看见读事务"这句话：read1 完成后 read2 才开始，read2 不能比 read1 旧，所以读之间也有顺序要求。这个质疑是对的，那句话确实漏了。然后我追了十几轮：读的 s 倒了怎么办、倒的那截里有没有写、100 到 100000 之间会不会有写、单机怎么理解、第三个观察者看到什么。中间讲的人每轮加新概念（safe time、linearizability 生效点、observer）没有止损，我说了"完蛋了我完全糊涂了我太笨了"，止损重开。重开后换成一步一问，四步走通，然后我自己构造了一个完整例子。推导链整理如下。

0. 为什么要紧。read1 完成后 read2 才开始，是不重叠的两个操作。linearizability 对它们的唯一要求：read2 返回的值不能比 read1 旧。刷新余额看到 100，再刷新看到 80，中间没人动账户，这就是"旧"，时间倒流。read2 比 read1 新、或一样，都允许。

1. 已完成的写，s < c。写事务挑了 s，等到真实时间 > s 才回复，回复那一刻叫 c。所以每个已完成的写 s < c。

2. read1 看见的每个写，s < t₁。read1 读的那一刻真实时间叫 t₁。它能看见的写只有那一刻已经完成的（没完成的写不进可读层，§4.2.1：commit wait 结束前 coordinator 不让任何副本 apply commit 记录）。已完成的 c < t₁，加第 1 步，s < c < t₁。

3. s_read2 > t₁。read2 在 read1 完成后开始，开始时真实时间 t₂ > t₁。read2 挑 s_read2 = latest ≥ t₂。所以 s_read2 > t₁。

4. 合起来。read1 看见的每个写 s < t₁ < s_read2，都在 read2 的"≤ s_read2"范围里。read2 全看见，不会旧。四步里 s_read1 一次都没出现，所以它和 s_read2 谁大谁小无所谓。

5. 精确版那句话。讲的人原来说"(s_read2, s_read1] 里没有已完成的写"，漏了时间限定，我指出"自相矛盾"。精确版：read1 读的那一刻，(s_read2, s_read1] 里没有 read1 看见的写。之后这一截可以被填上，填进去的写两个读都没看见。后来的写 s 比 read1 的 s 小，可以发生，从来不是要排除的；要排除的只是"read1 看见的写 read2 没看见"。

6. "旧"的精确含义。值 1→2→3，read1 返回 3，read2 返回 2，这就是旧。要成立需要 read2 没看见写 3，但写 3 被 read1 看见了，s₃ < t₁ < s_read2，矛盾。读返回的是看见的里 s 最大的，read2 看见的 ⊇ read1 看见的，最大值 ≥ 3。

7. 我自己构造的完整例子。write1 [1,4] t=2 s=4 / read1 [3,12] t=5 s=12 / write2 [6,8] t=7 s=8 / read2 [9,11] t=10 s=11，四个依次发生。read1 s=12 看不见 write2（读的时候 write2 不存在），read2 s=11 看见 write2。read1 的 s 大却看得少，合法。串行顺序 w1→r1→w2→r2 和真实时间一致。

8. 我的收口。"这不是废话吗，read2 物理上在后面当然能看到 read1 看到的一切。"对，是废话，但只在 Spanner 里成立。普通分布式数据库不成立：落后的副本、慢时钟挑小戳、上一篇 4(a) 的 Postgres repeatable read 事务。Spanner 靠三样让它成立：写的 commit wait、读挑 latest、副本的 t_safe。证明是在证"设计让显然的事真的显然"。

9. 另一个收口。"所以 selected timestamp 不会 expose 给 outside。"对。外部观察者只看见调用、返回、返回值，s 是内部挑版本的标签，linearizability 判定不用它。读的 s 比大小没意义，只有写的 s 钉在版本上。

教训给讲的人：他追问时每轮加新概念是崩掉的原因；该先立住"真实时间 / 区间 / 戳"三样东西的表，一步一问。

第 2 站 · external consistency 与为什么"读最新"不够

external consistency = linearizability（§1 原话）= strict serializability（FAQ）= 上一篇第 6 站那张表里"serializable + 顺序和真实时间一致"。我上一篇的总结是"serializable 管 transaction、linearizable 管 consistency，两个范畴"，Spanner 是把两个范畴叠在一起的系统。FAQ 的例子：Hatshepsut 在圣何塞改密码，口头告诉 Cassandra，Cassandra 在圣马特奥登录，必须看到新密码。

只读事务直接读最新已提交的值不够：T3 读 x 时 T2 没提交、读 y 时 T2 提交了，半个 T2，read skew。修法是 snapshot isolation 带时间戳：

                      x@10=9         x@20=8
                      y@10=11        y@20=12
T1 @10:  Wx  Wy  C
T2 @20:                   Wx  Wy  C
T3 @15:              Rx              Ry      ← 两个读都来自 @10，等于串行 T1 → T3 → T2

T3 读 y 时 T2 已 commit，T3 却读旧的，合法，因为 T3 和 T2 concurrent。全部问题归结为：给每个事务发一个戳，使 T1 真实时间先结束、T2 后开始 ⇒ s₁ < s₂。单机用计数器，跨几百个 leader 计数器不可比，只能用物理时间。

三种发号对照（我问出来的）：zxid = (epoch, counter)，逻辑，单 leader，严格有序；Snowflake = (毫秒, 机器号, 序号)，物理，多机各发，顺序不可靠（DDIA 脚注）；Spanner 要 Snowflake 的分布式 + zxid 的可靠。

我两次指出讲的人的漏洞，都对：① TT.now() 不是网络调用，对表每 30 秒后台一次，往返延迟进 ε 的起点，之后本地读表加漂移；区间只对调用那一瞬间成立，所以第 4 站两条规则都写成"在事件之后调"。② "已经发生的往返时间不代表这一次的 latency"：没有"这一次"，只有那一次对表，本次往返实测 2 秒 → 真实时间在 [10:00:00, 10:00:02]（FAQ 原推导），没有一处用过去的延迟估未来。漂移上限 200 µs/s 是硬件规格事先定的，对表时实测超了就踢机器。AWS Time Sync 默认是很准的 NTP（Snowflake 一类），开 ClockBound 才是 TrueTime。

第 4 站（心脏站）· 读写事务的戳

正确顺序（我说"如果以前按照时间排序其实就很好理解了"，讲的人顺序反了）：

① 版本带戳按戳读        x@10=9, x@20=8，拿 15 读到 x@10
② 要的性质              先 commit 的戳 < 后开始的戳
③ 戳是标签不是测量值     标签 ≥ 真实时刻（取 latest）
④ commit wait           回复前等到真实时刻 > 标签（≈ 2ε，和 Paxos 复制并行）

没有 commit wait 的反例：T1 在 .000 读到 [.000, .010]，取 s₁ = 10，立刻回复；客户端 .004 发 T2，T2 时钟慢读到 [.000, .008]，取 s₂ = 8 < 10。只读事务挑 9 看见 T2 看不见 T1。病根：s₁ = 10 是"最晚可能"，不是"已经过去"。

commit wait：T1 拿到 10 后反复问时钟，直到区间下端 > 10（[.011, .021]），才回复。回复时真实时间 ≥ .011 > 10，戳落在回复严格之前。T2 之后开始，latest ≥ 真实时间 > 10。

为什么取 latest 不取 earliest：earliest 第一条（戳 < 完成）天然满足不用等，但第二条（戳 ≥ 开始）坏了：T0 用 latest 完成戳 .008，T1 之后开始取 earliest .000 < .008。每个写事务同时是前人的后来者和后人的前人，两条都要。等能补第一条（推迟完成），补不了第二条（开始已发生）。我的总结："一种 single selection method 保证顺序有传递性，不存在"。Spanner 是挑（latest，不偏早）+ 等（动作，改变"完成"的时刻，不偏晚）。

"完成"的定义是 wait 结束。wait 没结束，数据虽然写进去了，锁没放、客户端没回复，对外等于没发生。"等太久 s₀ > s₁"构造不出来：等多久就把完成推迟多久、把"T1 在我之后开始"的门槛抬多高。多等永远安全，少等才危险。

两种单调分开：同 group 内（计数器 + lease disjointness，zxid 做法，不需要 TrueTime）vs 跨 group（Start rule + Commit Wait，必须 TrueTime）。没有 TrueTime = 几百个独立 ZooKeeper 互相没法比。

第 5 站 · 只读事务与 safe time

幕 1：只读事务开始时调一次 TT.now() 取 latest 当 s_read，不等。写事务四步（取 latest / 写 / 等 / 回复），只读三步（取 latest / 读 / 回复）。取 latest 人人做（我看见前人），等只写事务做（后人看见我）。读不等的精确理由（我质疑后改的）："读不等，不是因为没人需要看见它，而是因为它看见的一切都已被写事务钉成过去，后来的读天然看得见。"

幕 2：副本可能落后。东京 leader apply 到 x@30，伦敦 follower 只到 x@10，读挑 25 去伦敦答 9，错。t_safe = 已 apply 的最后一条写的 s，读 s_read ≤ t_safe 才答。两前提：leader 发戳随 index 单调（Spanner 加的），follower 按 index apply（Raft 原有）。Raft 格子里三个数分开：term（逻辑，选举）、index（逻辑，Raft 原有）、戳（物理，Spanner 加的）。我的对应：Flink watermark，连只涨不缩和 idle source 都一样。

和上一篇的 2PC 比四处变化：coordinator 是 participant 之一；client 发 PREPARE 并带着写的值（避免跨广域网发两遍）；"写盘"变成 Paxos 写到多数派（leader 崩新 leader 从 log 接着等）；COMMIT 后多一个 commit wait。p_B：B 对 coordinator 说"commit 戳别比我这个数小"，保 B 的 log 戳单调（t_safe 的前提），A 取 max。t_safe 第二个分量：B 上 T prepared 没结局时，只读 R（s=55）该不该看见 T 取决于 s 定成 53 还是 60，B 不知道所以不答；t_safe = min(已 apply 最大 s, 所有 prepared 的 p 最小值 − 1)。我的对应："还是 watermark，两个输入流取 min。"

wound-wait：老事务要新事务的锁直接杀新的，新要老的才等，只有"新等老"一个方向不成环。lease disjointness：新 leader 的票开始 > 旧 leader 的票结束，各自只在票内发戳，换 leader 不倒。票的两端都从 TT.now() 挑，到期判断用 TT.before（区间整个在左边才发，压着就不发，保守让出模糊地带，和 commit wait 镜像）。lease 和 p_B 是同一类：一个防换 leader 弄倒，一个防跨 group 2PC 弄倒，都在给"单 group 戳单调"补洞。坏场景：log y@50 后来了 y@45，t_safe 已说过 ≤50 全到，戳 48 的读一次 y@40 一次 y@45。

7. 通用原则清单

  1. 戳是标签不是测量值。T1 用 .010 做戳，真实发生的时刻不知道；只需两条：标签 ≥ 挑戳时的真实时刻，回复时真实时刻 > 标签。标签不精确，但先后和真实一致。
  2. 没有共同的时钟，但有共同的真实时间。两台机器的读数不可比，但"T2 在 T1 回复之后开始"这个事实对所有人成立；用等待把不确定的读数变成确定的先后。
  3. 挑 latest 是为了看见前人，等是为了被后人看见。每个写事务同时是前人的后来者和后人的前人，两条都要；读事务只有前一条，所以不等。
  4. 单靠从区间挑一个数做不到传递性，挑 + 等才行。等是动作不是选择，它改变"完成"这个事件发生的时刻；等只能修"戳太晚"，修不了"戳太早"，所以必须挑 latest。
  5. "完成"= 对外可见的那一刻。wait 没结束，数据在但锁没放客户端没回复，对外等于没发生；等多久就把完成推迟多久，所以多等永远安全。
  6. 读的戳比大小没意义，只有写的戳钉在版本上。读之间只需"看见的写不倒退"，这由写的 commit wait 保证，读自己什么都不用做；读的戳不暴露给外部，linearizability 判定只看返回值。
  7. 副本靠 watermark 判断够不够新，前提是写按戳单调到达。任何会打破单调的地方（换 leader、跨 group 2PC）都要补洞（lease disjointness、prepare 戳）。
  8. in-doubt 的事务拖住的不只是写者，还有读者。投了 YES 没结局的 T 让 t_safe 卡在它的 prepare 戳之前，戳越过它的读全等；修法是按 key range 细分。
  9. ε 大是性能问题，区间不包住真实时间是正确性问题。前者多等、不出错、可发现；后者安静地返回错值、没有报错、事后不可修。
  10. 每个系统都押一个假设，区别在破了掉 liveness 还是掉 safety。Raft/2PC 的 safety 不依赖任何假设；Spanner 把 safety 押在时钟上，所以要用运维把它压到比硬件故障还低。掉 safety 的假设要么别押（3PC 的下场）要么压低且可监控。
  11. TrueTime 不代替 Raft，是加在几百个 Raft group 之上解决"共同时间轴"一个问题。解决的是跨 shard 不是跨数据中心；只有一个 group 或不需要跨 group 一致读，整套可以不要。
  12. 不分片就没有这个问题。一台机器的 txid 天然全局，snapshot isolation 就是全部；Spanner 为必须分片的人设计。先问装不装得下，再问要不要 Spanner。
  13. 区间只对调用那一瞬间成立。所有规则都写成"在事件之后调 TT.now()"，不能提前算好存着用；"票到期了没"用 TT.before，压着模糊地带就当到期。
  14. 解释一个有多层时间的东西，先把"时间"拆成几个词。这篇我定了 s / t / c，定完之后前面几十轮的纠结一次收干净。
